## Установка

Запускайте на машине, которая будет держать сервер туннеля:

```sh
curl -fsSL https://raw.githubusercontent.com/SpecFlowdev/slipstream-installer/main/install.sh | sudo bash
```

Скрипт спросит домен туннеля, предложит поставить за ним SOCKS5-прокси и в конце напечатает всё, что нужно клиенту.

```sh
sudo ./install.sh --uninstall   # остановить и удалить всё, что он поставил
./install.sh --help             # все параметры и переменные окружения
```

## Запуск без вопросов

Любой ответ можно задать заранее — тогда скрипт годится и для системы автоматической подготовки серверов. Без разумного значения по умолчанию остаётся только домен:

```sh
SLIPSTREAM_DOMAIN=t.example.com sudo -E ./install.sh
```

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `SLIPSTREAM_DOMAIN` | — | Домен туннеля. Обязателен, если спрашивать не на чем |
| `SLIPSTREAM_DNS_PORT` | `53` | Порт, на котором слушать DNS |
| `SLIPSTREAM_SOCKS` | `y` | Ставить ли SOCKS5-прокси как цель туннеля |
| `SLIPSTREAM_SOCKS_PORT` | `1080` | Локальный порт этого прокси |
| `SLIPSTREAM_SOCKS_USER` | `slipstream` | Логин прокси |
| `SLIPSTREAM_SOCKS_PASSWORD` | генерируется | Пароль прокси; берётся из прошлой установки, если она была |
| `SLIPSTREAM_TARGET` | — | Слать трафик в свой сервис вместо устанавливаемого прокси |
| `SLIPSTREAM_SYSCTL` | `y` | Поднимать ли буферы UDP-сокетов |
| `SLIPSTREAM_FIREWALL` | `y` | Открывать ли DNS-порт в `ufw` или `firewalld` |
| `SLIPSTREAM_VERSION` | `v0.1.1` | Какой релиз upstream ставить |

Ещё три уходят прямо в `slipstream-server`:

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `SLIPSTREAM_MAX_CONNECTIONS` | `256` | Одновременных подключений к туннелю |
| `SLIPSTREAM_IDLE_TIMEOUT` | `60` | Через сколько секунд простоя рвать соединение |
| `SLIPSTREAM_FALLBACK` | выкл | `HOST:PORT`, куда переслать пакеты, которые **не являются DNS** — так DNS-порт можно делить с другим сервисом. Обычные DNS-запросы slipstream в любом случае отвечает сам |

## Требования

- **Linux с systemd**, x86_64 или arm64
- **Root** — чтобы установить сервис и занять DNS-порт
- **Свой домен**, чью `NS`-запись можно направить на этот хост. Берите покороче: полезная нагрузка клиента на запрос равна `(240 − длина домена) / 1.6` байт, так что чем короче домен, тем быстрее туннель
- **Доступный UDP** на порту прослушивания, по умолчанию 53

## Зачем этот установщик

- **Готов к работе сразу** — предлагает поставить SOCKS5-прокси как цель туннеля, так что подключившийся клиент попадает в рабочий прокси, а не в порт, за которым ничего нет.
- **Без компиляции** — ставится готовый бинарник из релиза. Сборка slipstream из исходников тянет picoquic, picotls и OpenSSL через CMake; здесь всё занимает секунды.
- **Спрашивает, а не угадывает** — домен и цель форвардинга запрашиваются при запуске, так что ошибиться в командной строке негде. Ввод читается напрямую с терминала, поэтому работает даже через `curl | bash`.
- **Вшитые контрольные суммы** — SHA256 каждого архива зашит в скрипт, а не просто скачивается рядом с архивом.
- **Не root во время работы** — сервис запускается под непривилегированным пользователем и биндит порт 53 через одну-единственную привилегию.
- **Разбирается с конфликтом на порту 53** — находит stub-listener `systemd-resolved`, который на Ubuntu и Debian молча ломает привязку к DNS-порту, и предлагает его отключить.
- **Настраивает хост** — предлагает поднять буферы UDP-сокетов: это сильнее всего влияет на скорость, и именно этот шаг обычно пропускают.
- **Открывает файрвол** — замечает работающий `ufw` или `firewalld` и предлагает пропустить DNS-порт, потому что закрытый файрвол выглядит ровно как сломанный туннель.
- **Проверяет, что порт реально занят** — активный unit это ещё не слушающий сокет: slipstream при неудачной привязке пишет предупреждение и продолжает работать, поэтому установщик смотрит на сокет, а не верит юниту.
- **Умеет удаляться** — `--uninstall` останавливает службы, удаляет юниты, бинарник и файл тюнинга, а про сертификат, который закрепили клиенты, спрашивает отдельно.
- **TLS настраивается сам** — сервер генерирует сертификат при первом старте. Ни CA, ни ACME, ни лишнего открытого порта.

## Настройка буферов сокетов

Туннель гоняет много мелких UDP-датаграмм. На загруженном канале стандартные
буферы сокетов переполняются, и отброшенные ядром пакеты выглядят для QUIC
как потери — он снижает скорость.

**Установщик предлагает сделать это за вас** и пишет тот же файл; ответьте
`n` или задайте `SLIPSTREAM_SYSCTL=n`, чтобы он не трогал хост. Руками это
выглядит так:

```sh
sudo tee /etc/sysctl.d/99-slipstream.conf >/dev/null <<'EOF'
net.core.rmem_max=26214400
net.core.wmem_max=26214400
net.core.rmem_default=26214400
net.core.wmem_default=26214400
EOF
sudo sysctl --system
```

Реально здесь работают два параметра с `default`: slipstream не вызывает
`setsockopt(SO_RCVBUF)`, поэтому его UDP-сокет получает ровно то, что задано
по умолчанию. Пара `max` лишь поднимает потолок, который приложение вправе
запросить, — её стоит выставить, чтобы ничто не упёрлось в лимит позже.

Учтите: `rmem_default` и `wmem_default` действуют на **все** сокеты хоста, то
есть вы меняете память всех процессов на пропускную способность туннеля. На
машине, где кроме туннеля ничего нет, это и требуется; на общем сервере
задайте только пару `max`, а значения по умолчанию не трогайте.

## Что устанавливается

| Путь | Содержимое |
| --- | --- |
| `/usr/local/bin/slipstream-server` | Бинарник сервера — его и запускает сервис |
| `/etc/slipstream/` | `cert.pem`, `key.pem` — создаются при первом старте |
| `/var/lib/slipstream/reset-seed` | Seed для stateless reset, переживает перезапуски |
| `/etc/systemd/system/slipstream-server.service` | Unit сервиса |
| `/etc/sysctl.d/99-slipstream.conf` | Размеры UDP-буферов, только если вы согласились на тюнинг |

Если включён SOCKS5-прокси, добавляется ещё два:

| Путь | Содержимое |
| --- | --- |
| `microsocks` | SOCKS5-сервер, ставится из репозиториев дистрибутива (`apt`, `dnf`, `pacman` или `apk`) |
| `/etc/systemd/system/slipstream-socks.service` | Unit прокси, слушает только loopback |
| `/etc/slipstream/socks-credentials` | Логин и пароль SOCKS5, права 0600 |

## Как к нему подключаться

Этот репозиторий ставит и настраивает **только сервер**. Клиент — отдельный проект: [SpecFlowdev/slipstream-client](https://github.com/SpecFlowdev/slipstream-client), десктопное приложение для Linux и Windows со своими сборками и документацией.

Всё, что нужно клиенту, готовится здесь, и установщик печатает это в конце работы:

| Параметр | Откуда берётся |
| --- | --- |
| Домен туннеля | То, что вы ввели при установке |
| Сертификат сервера | `/etc/slipstream/cert.pem` — скопируйте на клиент; это публичные данные, не секрет |
| Логин и пароль SOCKS5 | Печатаются в конце, лежат в `/etc/slipstream/socks-credentials` |

## Безопасность

**Вшитые контрольные суммы.** Архивы релиза сверяются с SHA256, зашитым в `install.sh`. Проверка только по файлу `.sha256`, лежащему рядом с архивом, не поймала бы подмену релиза: тот, кто может заменить одно, заменит и другое. При установке версии, отличной от штатной, скрипт откатывается на опубликованную сумму этого релиза и честно об этом предупреждает.

**Не root во время работы.** Сервис работает под непривилегированным системным пользователем `slipstream`. Право занять порт 53 даёт одна лишь `CAP_NET_BIND_SERVICE`, а не запуск от root; `NoNewPrivileges` закрывает повышение привилегий.

**Изоляция.** `ProtectSystem=strict` с `ReadWritePaths`, суженным до собственных каталогов конфигурации и состояния, плюс `PrivateTmp`, `PrivateDevices`, `ProtectHome`, `ProtectProc=invisible`, защита ядра, cgroups и часов, `RestrictAddressFamilies=AF_INET AF_INET6`, `MemoryDenyWriteExecute` и seccomp-фильтр `@system-service`.

**Docker нет — намеренно.** Upstream не публикует контейнерный образ. Установка через Docker добавила бы в поверхность атаки root-эквивалентный сокет демона, ничего не выиграв по сравнению с изоляцией выше.

**Сертификаты.** Сервер при первом старте генерирует self-signed сертификат на P-256, а клиент пиннит именно этот leaf. Никакому CA доверять не нужно, порт под ACME-проверку открывать тоже.

**Туннель не аутентифицирует клиентов.** Пиннинг сертификата подтверждает клиенту подлинность *сервера*, но не наоборот — сервер принимает любого клиента, который прошёл рукопожатие. Значит, кто узнал ваш домен туннеля, тот подключится и доберётся до того, что стоит на цели форвардинга. Поэтому SOCKS5-прокси ставится с логином и случайным паролем на 24 символа: он генерируется при установке и сохраняется в `/etc/slipstream/socks-credentials`. Если направите туннель на свой сервис вместо прокси — контроль доступа придётся обеспечить ему самому.

**Секретность домена — не средство контроля.** Делегирование зоны через `NS` публикует домен по определению, а запросы приходят от тех рекурсивных резолверов, которыми пользуются ваши клиенты, так что фильтровать по адресу источника тоже нельзя. Длинный случайный поддомен проблему не решает — устойчивый трафик туннеля всё равно всплывает в passive DNS, — зато напрямую бьёт по скорости: полезная нагрузка клиента на запрос равна `(240 − длина домена) / 1.6` байт, то есть каждый лишний символ домена оплачен пропускной способностью. Границей безопасности считайте авторизацию на цели форвардинга, а не домен.

**Прокси напрямую наружу не смотрит.** `microsocks` слушает только `127.0.0.1`, то есть из сети недоступен — попасть можно через туннель или с самого хоста. Работает под `DynamicUser` — одноразовая учётка с пустым набором capabilities и без доступа к приватному ключу сервера. Пароль не виден в `ps` (microsocks сам затирает свои аргументы) и не лежит в общедоступном файле (unit с правами `0640`), но любой локальный пользователь хоста всё же может обратиться к порту прокси.

## Управление сервисом

```sh
systemctl status slipstream-server      # состояние
journalctl -u slipstream-server -f      # смотреть логи
systemctl restart slipstream-server     # перезапуск
```

## Удаление

```sh
sudo ./install.sh --uninstall
```

Останавливает и выключает обе службы, удаляет unit-файлы, бинарник и файл
sysctl, убирает пользователя `slipstream`.

Сертификат — это то, что закрепили у себя клиенты, поэтому `/etc/slipstream`
и `/var/lib/slipstream` **сохраняются, если вы не скажете иначе**: удалить их
значит выдавать новый сертификат каждому настроенному клиенту. Скрипт
спрашивает и по умолчанию оставляет.

Две вещи он сознательно не трогает и сообщает о них в конце: правило
файрвола, если добавлял, и отключённый при установке stub-listener
`systemd-resolved`. Убирать их — решение о самом хосте, а не о туннеле.
`microsocks` пришёл из вашего пакетного менеджера и удаляется так же, если он
больше не нужен.
